# Desmaptic widgets

Desmaptic turns an iPhone or iPad into a grid of glass buttons that control a Mac. A button runs a command when tapped — and it can also *show* something: a plain face (icon, title, color) or an **SVG face**, a drawing over the whole button that the phone animates between the frames a script sends. You reach all of it through the `desmaptic` MCP server.

This skill is the craft. The reference — which SVG the engine draws, tool schemas, the HTTP API — lives in the MCP tool **`get_available_actions`**. Ask it for the topics you need — `svg` for faces, `scripts` for loops and the live-update API, `audio`, `notifications`, `buttons` for commands and sizes; without topics it lists them — and trust it on those facts. How to choose a button's face is decided here, in §1. Do not guess at supported SVG from memory of browsers: the engine draws a subset, and tells you what it ignored.

## 1. Decide the face in one step

Most requests need a plain button. Pick fast, from what the content *is*:

| The button shows… | Face | Typical size |
|---|---|---|
| an action (launch, hotkey, script), a name, an on/off state, text, **a single number the user reads as a number** ("main ↑2", "28°C", "$64,210", "412 GB free", "3 unread") | **plain** — `title`, icon or emoji, color | 1×1 |
| **a share of a whole that the user reads as a level**: CPU load, memory pressure, battery, volume, "how full is the disk", progress, time left of a timer | **SVG** — ring, bar, gauge | 1×1 |
| one value **and** its history or trend | **SVG** — value + sparkline | 2×1 |
| several values read together, a clock, a heatmap, a small chart | **SVG** | 2×2 |
| a picture that does not change: a logo, a drawn glyph, an icon exported from Figma | **saved SVG face**, no script | 1×1 |
| one picture across many buttons (a tank, a sky, a skyline) | **SVG scene**, one script for the page | a page of 1×1 |

Words that point to SVG — only when they describe what the *button* shows: graph, chart, gauge, ring, progress, sparkline, history, trend, animated, a percentage or a countdown. The name of a page or profile ("on my Dashboard page") is not a signal. Words that point to plain: simple, minimal, "just the number", a list of words, long text.

The table is about what the *user asked to see*, not about the metric. The same disk gives "how much space is left" → a number → plain ("412 GB free"), and "how full is it" / "show it as a ring" → a level → SVG. A number with a unit is already the answer to "how much is left"; a ring adds nothing to it and costs a script that draws frames. Reach for SVG only when the request names a level, a share, a shape, or a change over time.

When it is unclear, build the **plain** one — it is never wrong, and it is one call to upgrade later. If you must ask, ask once, and ask about the *content* ("only the current value, or the last minute as well?"), never about the format: "do you want an SVG face?" means nothing to the user. Describe what you will draw in their words — "a ring that fills with CPU load, the number in the middle".

## 2. The workflow

1. **Look at the deck.** `get_profiles`, then `get_page_layout`: the page id, an occupancy map, the button UUIDs and the free positions for every button size, in a few hundred bytes. Take a position from its `free` list — never invent one: a place that is taken makes the whole call fail, with the free places listed. Its `connectedDevice` says which grid is on the user's screen: the pad grid (an iPad, or an iPhone Duo unfolded) shows two extra columns (`padOnly` positions) — ordinary room there; the phone grid (an iPhone, or a Duo folded) does not show them; ask when the kind is unknown. Read `get_profile_detail` with `pageName` only when you need what the buttons *do* (a widget page is tens of KB of scripts, a whole profile hundreds). No room where the widget belongs? Buttons can be moved and resized (`row` / `col` / `rowSpan` / `colSpan` in `update_buttons_by_uuid`); deleting is left to the user.
2. **Pick the size from the content** (table above), not from habit. One number fits 1×1; never squeeze a 2×2 design into 1×1 — text smaller than the standard button label is the most common reason a widget gets rejected. Sizes, viewBox per size and minimum text sizes: `references/svg-craft.md`.
3. **For a live widget, write one inline script** and pass it as `startupScript` — the agent starts it when the phone connects and keeps it alive, no timeout. Tap scripts (`scriptCode`) die after 60 s and are for actions. Start from `assets/widget_template.zsh`; the reasons behind every line of it are in `references/live-widgets.md`.
   - Write it in **zsh** with what every Mac has — awk, sed, curl, jq, osascript, iostat. `python3`, `swift` and `git` come only with the Command Line Tools: on a Mac without them `/usr/bin/python3` is a stub that opens an install dialog every time the script runs (and the agent restarts a failing script every minute). `command -v` finds the stub, so a script that really needs python checks `xcode-select -p` first, as `assets/scene_template.zsh` does.
   - The whole script goes **inline** in the parameter. The button's config lives on the user's iPhone and iPad (synced through iCloud) and runs on every Mac they connect to; a file under `$DESMAPTIC_STORAGE` exists on one Mac only. A button that calls a script file is broken on the next Mac.
   - It talks to `http://127.0.0.1:9848` with the token from `$DESMAPTIC_TOKEN`, and the token never goes on a command line — any app on the Mac can read command lines. The curl form and the reasons: `references/live-widgets.md` → The runtime API.
   - When it depends on something that can fail — the network, an API key, another app — it **says why** it stopped working through `/api/error` (on a change, and `clear` once it works again) instead of leaving a value that silently stops changing: `references/live-widgets.md` → Saying why it does not work.
4. **Give an SVG widget a saved face** — the `svgFace` parameter: one frame of the same template with neutral numbers (empty ring, flat line, "–"). The button then shows the widget from the moment the app opens, the first live frame glides out of it, and it is what remains when the script stops. Same structure as the live frames, or it cross-fades instead.
5. **Look before you deliver.** Call `render_preview` with the frame: it draws it the way the phone does and returns the picture and, under it, every parser warning — the goal is none. No device, no approval. Layout mistakes (text over a ring, a label off the button, a stripe nobody can see) are invisible in the source and obvious in the image; the picture is about twice the phone's size, so judge text by the minimum sizes in §3, not by eye. For a live widget pass two states as `svg` + `nextFrame` (0 % and 100 %; two consecutive frames of anything that loops) and the `easing` the frames will carry: the reply says whether they glide or cross-fade, and the picture is a storyboard of the glide — check the middle frames for a hand turning the long way or a shape flying back. A landscape layout is previewed by a separate call. (With a shell and a connected phone you can also post a frame to the agent — `references/troubleshooting.md`.)
6. **Read your own call once more** — the mistakes that still slip through, each one checkable in the text you are about to send:
   - every frame the script can produce comes from the *same* template (same elements in the same order) — including the first frame, the "no data yet" frame and the saved `svgFace` (the one exception: a scene page keeps light saved faces and cross-fades once at start — `references/scenes.md`); a list that grows (history points) is padded to its full length from the start;
   - state files live under `$DESMAPTIC_STORAGE/<widget>/`, never in `~` or `/tmp`, and hold timestamps, not counters;
   - the size the user asked for is the size you deliver ("big" timer = 2×2), and a non-square button has its landscape layout;
   - the script is zsh (or bash) and calls no `python3`, `swift` or `git` — unless it checks `xcode-select -p` first and exits with the reason without them;
   - the token appears only as `$DESMAPTIC_TOKEN` read from the environment: in curl through `curl -q … --variable '%DESMAPTIC_TOKEN=' --expand-header 'Authorization: Bearer {{DESMAPTIC_TOKEN}}'` (`-q` first: no `~/.curlrc`), in a script that talks HTTP itself (zsh/net/tcp) as a header it writes — never `-H "Authorization: Bearer $DESMAPTIC_TOKEN"`, never a pasted value; every URL is `http://127.0.0.1:9848/…`;
   - exactly one script writes each button's face; a script that draws *other* buttons needs their UUIDs: give each new button a `ref` and write `{{CELL_ID:<ref>}}` in the script — the tool puts the UUIDs in before sending, so it is one `add_buttons_to_client` call and one review (`references/interaction.md`).
7. **Deliver** with `add_buttons_to_client` (new buttons), `update_button_by_uuid` / `update_buttons_by_uuid` (existing ones), `add_pages_to_client` (a new page). Every delivery waits for the user to tap **Accept on the phone** — say so, and do not retry while it waits. A result with `status: pending` (UNKNOWN) is not a rejection: the review is still on the phone and a late Accept applies it — once the user says they answered, call `get_delivery_status` with its `deliveryId` instead of sending anything again. `busy` means another change waits on the phone (one per Mac). The result's `notes` carry engine warnings about the saved face: read them.
8. **Look at it working**: a few seconds after Accept, `view_live_button` draws the frames your script really posted and the phone's glides between them, with their timing — once, not in a loop. Fix what it shows (a glide cut short, a cross-fade and the element that caused it, a hand turning the wrong way) before calling the widget done. It replays each glide from the frame before, not from what the phone had on screen when the next frame came, so it cannot show a mover's halves parting at a button border or an entering mover running ahead: those you prevent in the frames themselves (`references/scenes.md` §4). A mover moved in the frame that hides it does show: a fading copy sliding across in the in-betweens.
9. **Tell the user what they got**: what the button shows, how often it updates, what a tap does. Not how it is built.

A script may update **any** button, not only its own (`cellId` is just a UUID). When the request involves more than one button that must react to each other — a timer and its Start key, a player and its display — read `references/interaction.md` before designing anything: who draws which button decides whether it feels instant or flickers.

Always set a meaningful `label` and a sensible icon even under an SVG face: the label is not drawn, but it names the button for VoiceOver and in every tool result, and it is what shows if the face cannot be drawn.

**A button that asks.** When a tap needs a text the user types at that moment, and the text must reach exactly this Mac or the Mac's focus must stay where it is — a note to an inbox, a bug for the tracker with the Mac's context, a question about the project — give the button an `input` (a question, a placeholder, quick replies): the phone asks before the tap runs. End its label with "…". The action gets the text only as data — a script reads `"$DESMAPTIC_INPUT"`, a URL or a typed snippet puts it where it says `{{INPUT}}`; never `eval` it, never paste it into code. How each action reads it: `get_available_actions` topic `buttons` → `buttonInput`. The card shows the button as its script draws it at that moment; while no text is wanted, the script can turn the question off (`skipInput` in `update-button`, topic `scripts`) — a tap then runs at once with an empty text.

## 3. What makes a face good — the five things that matter

- **Same structure, different numbers.** The phone glides between two frames only when they have the same elements, ids and path commands; then positions, sizes, colors, opacity, dash offsets, gradients and clips all interpolate, and text swaps at once. Anything else cross-fades, and reads as a blink. So write **one template function** and change only numbers and text in it. Hide with `opacity="0"`, never by removing an element; to move a hidden element, hide it in place first and move it in a later frame. Details and the safe building blocks: `references/svg-craft.md`.
- **The phone animates, you do not.** Send a frame when the data changed — every 2–5 s for system metrics — with a `duration` clearly shorter than that interval, so the button rests most of the time. Only motion that never rests (a ticker, a spinner, a scene's movers) uses `easing: "linear"` with a `duration` of 1.25 × the loop's measured period (1.2–1.35×): over Wi-Fi frames come in bursts, up to ~0.15 s late, and a glide that ended before its frame stops the motion for a moment, while one still running is taken over at the same speed — the price is a steady lag of a quarter step. A scrolling chart's rest + slide keeps × 1.0–1.1 (`references/svg-craft.md` → Sparkline).
- **Count what glides at the same moment.** A widget that rests between its frames is light; motion that never rests (a ticker, a scroll, a spinner, a scene) keeps the phone busy for as long as it runs. A handful of always-moving cells per page is fine, a wall of them is a stress test — prefer one 2×2 widget to many 1×1 widgets that all move every second. On a face that moves all the time, draw with flat colors, `rect` / `circle` / `ellipse`, text and square-cornered gradient `rect`s, and keep gradient strokes, masks and shaped clips off it. Keep every `path`, `polygon`, `polyline` and `line` within one cell and its shape unchanged while it glides — move it whole by `transform`, not by its points; cut long shapes to each cell and draw large areas as `rect`s. The rules: `references/svg-craft.md` → Keeping the phone smooth; their exact limits: `get_available_actions` topic `svg` → `widgetFaces.budget`.
- **Readable at arm's length.** On a 1×1 or 2×1 the face is drawn at roughly 0.40×: text at least 28 units in a 200-unit viewBox, the main value 56–64. On 2×2 (≈ 0.88×): labels ≥ 16, values ≥ 22. One idea per button.
- **Rectangular buttons need two layouts.** In landscape the grid turns and a 2×1 becomes 1×2. Send `landscapeSource` (live) or `svgFaceLandscape` (saved) with the same data laid out for the transposed shape — or choose a square size.
