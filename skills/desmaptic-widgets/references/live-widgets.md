# Live widgets: the script behind the button

A live widget is a button whose `startupScript` loops forever and posts what it sees to the agent. This file explains the lifecycle and every decision baked into `assets/widget_template.zsh`, so you can change the template without breaking it.

## Which script slot

| Slot | Parameter | Runs | Limit | Use for |
|---|---|---|---|---|
| startup | `startupScript` | when the phone connects, for every button of the ACTIVE profile, whatever page is on screen | none — restarted if it crashes | the widget's loop |
| tap | `scriptCode` (with `commandType: shellCommand` / `appleScript`) | on tap | killed after 60 s | an action; changing the widget's state |
| long press | `longPressScriptCode` | on long press | 60 s | a second action |

Let the startup loop own the drawing. A tap should change *state* — write a small file under `$DESMAPTIC_STORAGE/<widget>/` — and the loop renders it on its next pass. Two scripts drawing on one button fight each other.

Lifecycle facts that shape the code:
- Started on connect, killed (SIGTERM, then SIGKILL after 2 s) on disconnect, started again on the next connect. Memory does not survive; persist what must to `$DESMAPTIC_STORAGE`.
- Exit code 0 means "done, do not restart". A crash is restarted with a growing delay (5 s … 60 s, forever). After five failures the phone lists the button among its errors (the ⚠ count on its toolbar opens the list) with your stderr — write the reason there. A failure the loop survives is not a crash: report it (Saying why it does not work, below).
- Switching the profile on the phone stops the old profile's scripts and starts the new one's.
- Never `nohup`, `disown` or `setsid`: the agent owns the process group and cleans it up.
- The loop runs whatever page is on screen. The agent knows what the phone shows: a frame for a hidden button is answered with `"visible": false`, is **not sent** — the agent keeps the button's latest state — and reaches the phone the moment the button is shown. So an **ordinary widget** (a frame every 1–5 s, or on change) **simply keeps drawing**: the phone pays nothing for it, and the button is current as soon as its page opens — the template does exactly this. A loop that sleeps while hidden shows a stale face for as long as it sleeps.
- **Rest only a loop that is expensive on the Mac** — a scene across many buttons, several frames a second, a widget that follows the sound, costly sampling (python3 or swift, network calls, `osascript` to other apps): while hidden, no sampling and no frames. Ask on **every tick**, so it wakes within one tick: `GET /api/view` returns `visibleCellIds` (the buttons shown in any of the phone's windows — an iPad can show several side by side), `activePageId` (the page of the window used last), `orientation` (`portrait` / `landscape`) and `isForeground` — `scene_template.zsh` does this. Check the button's own id in `visibleCellIds`, not its page against `activePageId`: a page open in the window beside is shown too. No `visible` key / `view: null` means an older app: treat the button as shown, never sleep on a guess.
- `"dropped": true` in the answer means the phone is **not reading** — the page gets more frames than the phone can draw, or an older phone app is suspended with the connection still open — and that very frame was not sent now. The agent does not queue frames for such a phone: it keeps only the **newest state of every button** (a `reset` or a face removal included) and sends it as soon as the phone reads again, so the last thing you posted always arrives and nothing needs resending; the frames in between are skipped. Each answer is about its own frame — no `dropped` key means it was sent. Slow down to one frame every couple of seconds while answers carry `dropped`, go back to your pace at the first answer without it, never retry in a tight loop. The template's pace never gets there; scenes, tickers and visualizers do. While the phone app is in front (`isForeground: true` in `GET /api/view`) — with a current app that is almost every `dropped`, as a button off screen or an app in the background gets `"visible": false` instead — `dropped` means the page costs more than the phone can draw. Keep the slow-down above, a continuous glide stretched to the slower pace, but the fix is a cheaper page: fewer cells gliding at the same moment, paths cut to their cell and unchanged in shape, no masks on what moves (`svg-craft.md` → Keeping the phone smooth). For continuous motion a slower tick by design does not help: every cell still glides, and the motion only gets jerkier. A falling `postsLastMinute` in `get_startup_script_status` is the same sign.
- Is it running? `get_startup_script_status` shows each script's state and, for one that died, the last 2 KB of its stderr — write the reason there. `restart_startup_script` runs the saved script again at once: no delivery, no tap on Accept.

## The runtime API

`POST http://127.0.0.1:9848/api/update-button` with `Authorization: Bearer <token>` and a JSON body. `{{CELL_ID}}` in the script text is replaced with the button's UUID before it runs; the token is in `$DESMAPTIC_TOKEN`, and `$DESMAPTIC_STORAGE` is in the environment too. Field list and limits: `get_available_actions` with topic `scripts` (`buttonAppearanceOverlay`).

**Secrets stay out of the script.** The deck syncs through iCloud, where only the Desmaptic app on the user's devices can change it. It is end-to-end encrypted only with Advanced Data Protection: keep passwords and tokens out of scripts — use files in `$DESMAPTIC_STORAGE` (not synced) or the Mac's Keychain.

**The token never goes on a command line.** Any app on the Mac can read the command lines of your processes, so `curl -H "Authorization: Bearer $DESMAPTIC_TOKEN"` hands the token out — the shell expands it into curl's arguments. The agent sets `$DESMAPTIC_TOKEN` for every script it starts, a token of that launch's own: it works while that script runs and stops working when it ends, so an app or a background job the script leaves behind cannot use it. When the agent restarts, resumes after another user's session or restarts its local API, running startup scripts are restarted with new ones. Never paste the token into a script (it stops working when the script it came from ends), never print or log it, never `cat ~/.desmaptic-mcp-token` into a command.
- **curl:** `curl -q -s -m 5 --variable '%DESMAPTIC_TOKEN=' --expand-header 'Authorization: Bearer {{DESMAPTIC_TOKEN}}' …` — curl reads the variable from its own environment. `-q` goes FIRST: it makes curl ignore `~/.curlrc`, where another program could plant a proxy or a trace that carries the token elsewhere. `{{DESMAPTIC_TOKEN}}` is curl's syntax, not Desmaptic's (the agent replaces only `{{CELL_ID}}`); the `=` gives an empty default, so a missing variable is a plain 401 instead of a curl error. `--variable` needs curl 8.3 or newer: macOS 15's `/usr/bin/curl` has it, an older curl earlier in `PATH` (conda, an old Homebrew) stops with a usage error — call `/usr/bin/curl` if unsure.
- **A script that talks HTTP itself** — zsh over `zsh/net/tcp` (the spectrum in `get_available_actions` topic `audio`), Swift, the python of the scene template: read it from the environment and write the header in code. `print` is a zsh builtin, so the request never becomes a command line.
- **URL:** `127.0.0.1`, not `localhost`.

`get_startup_script_status` lists a startup script that puts the token on a command line or carries a pasted one under `notes`.

A button script may call `update-button`, `notify`, `error`, `view`, `status` and `audio/levels` (below). The rest of the API — config, deliver, probe, scripts, restart-script — answers a script with 403: that is the MCP tools' business, done over the agent's private socket. A `401` means no valid token: a pasted or old one, the token of a script that has already ended (something it left running), or an empty variable.

A plain live button needs only `title`, `icon` or `emoji`, `color`. The title wraps at spaces onto at most two lines; there is no line-break character (a `|` is shown as it is), so keep it to a few short words:

```bash
#!/bin/bash
# Disk free, every 60 s
API=http://127.0.0.1:9848/api/update-button
post() { curl -q -s -m 5 --variable '%DESMAPTIC_TOKEN=' --expand-header 'Authorization: Bearer {{DESMAPTIC_TOKEN}}' \
           -H "Content-Type: application/json" -d "$1" "$API" >/dev/null; }
trap 'post "{\"cellId\":\"{{CELL_ID}}\",\"reset\":true}"; exit 0' TERM
while true; do
  FREE=$(df -g / | awk 'NR==2{print $4}')
  post "{\"cellId\":\"{{CELL_ID}}\",\"title\":\"${FREE} GB free\",\"icon\":\"internaldrive.fill\",\"color\":\"#34C759\"}"
  sleep 60
done
```

Anything with quotes or user text in it (an SVG document, a song title) must be escaped for JSON — `jq -n --arg` (`/usr/bin/jq` is on every Mac the agent runs on), or by parameter expansion like `json()` in the template, which costs no extra process per frame — never spliced into the body as it is.

## Saying why it does not work: `POST /api/error`

A widget that cannot get its data — no network, a refused key, the app it talks to is closed — must say so. Otherwise the button simply stops changing, and the user cannot tell a quiet value from a broken one. Post `{"cellId": "{{CELL_ID}}", "kind": "<kind>", "message": "<a few plain words>"}` to `/api/error` with the same token rule. The phone names the kind in the user's language with what to do about it, puts your words under it and counts the failing buttons on its toolbar. Nothing is drawn on the button, so keep the last good face — dim it or show `—` only when an old value would pass for a current one. The kinds, the fields and the answers: `get_available_actions` topic `scripts` → `errorReports`.

- **About your own button.** `cellId` is the button whose script reports: a report lasts as long as that button's script runs. A script that draws several buttons reports once, on its own button.
- **Report on a change, clear once.** Keep the last kind and message in a variable, post only when they differ, and post `{"cellId": "{{CELL_ID}}", "clear": true}` once the call works again; remember a report only once the agent answered 200, so a 503 (no phone) is posted again on the next pass — the guide's `report()` does exactly that. The agent folds repeats (the phone gets at most one update a second per error), but a post on every pass still costs the loop a curl.
- **Pick the kind by what the user should do:** `auth` when a key must be renewed, `config` when the button must be edited, `permission` / `accessibility` / `automation` when macOS must allow it (the phone then offers to open that pane on the Mac), `network` / `timeout` / `notRunning` when it is out of the user's hands for now.
- **A tap or long-press script** posts the reason and exits 1: the toast after the press says your words instead of the stderr.
- **A crash needs no report.** A startup script that keeps dying is listed with its stderr, a failed press with its stderr, a frame the agent refused with the reason of the 400. `get_startup_script_status` shows what a script reported too (`reportedErrors`).
- Words for the user, not a stack trace — and never a token, password or code.

## Why the template looks the way it does

- **`#!/bin/zsh` on the first line.** A script that starts with a shebang is run by that interpreter; without one it runs under zsh anyway (from a private temporary file, so its text is never on a command line). zsh, awk, sed, curl, jq, osascript, iostat, vm_stat and pmset are on **every** Mac; a zsh loop sits at a few MB. The environment is fixed: `PATH` is `/usr/bin:/bin:/usr/sbin:/sbin:/opt/homebrew/bin:/usr/local/bin` (a tool in `~/.local/bin`, such as `claude`, needs `export PATH="$HOME/.local/bin:$PATH"`), and zsh runs with `-f` — no `~/.zshenv`, `.zprofile` or `.zshrc`.
- **Apps start with `env -i`.** An app the script starts — with `open`, or with an Apple event or `activate` to an app that is not running, System Events included — inherits the script's environment, `$DESMAPTIC_TOKEN` included, and a terminal hands it to every shell it opens. Start apps with `env -i /usr/bin/open -b <bundle id>` (or `-a`, `-R`, a URL) and run AppleScript that may start one as `env -i /usr/bin/osascript -e "$script" <args>`: the app then gets the account's own environment, as from the Dock. Hand that osascript its data as arguments (`on run argv`) or on stdin, never as `env -i NAME=value` — that puts the value on a command line any app of the account can read. An `appleScript` tap runs with that environment too (the token only when its text names `$DESMAPTIC_TOKEN`), so a tap that starts or drives another app is a `shellCommand` running `env -i /usr/bin/osascript`.
- **No `python3`, `swift` or `git`.** They come only with the Command Line Tools (or Xcode). On a Mac without them `/usr/bin/python3` and the others are stubs that open an install dialog every time they run — and the agent restarts a failing startup script every minute, so the dialog would keep coming back on every Mac the phone connects to. `command -v python3` finds the stub, so it proves nothing. When python is worth that condition (a scene with 32 frames of gradients), check `dev=$(xcode-select -p 2>/dev/null) && [[ -x $dev/usr/bin/python3 ]]`, without the tools exit 1 with the reason on stderr (the phone's list of errors shows it), with them `exec "$dev/usr/bin/python3" -I - <<'PY'` … `PY` — `assets/scene_template.zsh` is built that way. Python runs isolated there (`-I`, `PYTHONNOUSERSITE=1`): stay with the standard library; when a package is essential, the script creates a venv under `$DESMAPTIC_STORAGE` on first run and calls its `bin/python` by full path. A `#!/usr/bin/swift` script needs the tools too and holds 150–300 MB per widget.
- **`export LC_ALL=C`, numbers from awk.** In a German or Russian locale `printf` writes `0,5`, which is not a number in SVG; zsh's own float arithmetic prints `0.17999999999999999`. The template computes every coordinate and colour in one `awk` call and formats it with `%.2f`.
- **One `frame()` function printing the SVG string.** One template means one structure, which is what lets the phone glide (see `svg-craft.md`).
- **Send the first frame before the loop**, then only when the value changed. The phone glides between frames by itself, and a frame that says the same thing buys nothing.
- **`duration` 0.6 s for a sample every ~3 s.** Long enough to look smooth on any device, short enough that the button rests most of the time.
- **A keyframe every 30 s even if nothing changed.** The face can disappear from outside while your loop keeps running — another script's `reset`, the user saving the button, a terminated tap process. The keyframe brings it back.
- **A frame counts as sent only on HTTP 200.** On anything else `last` stays as it was, so the next pass retries: the agent may be restarting, the phone may be away.
- **Send `duration`, `easing` (and `fit`) with every frame.** They belong to the face currently on the button and are lost with it.
- **Read the body of a 400 and print it to stderr.** That is the engine telling you the line and the reason. The phone lists a refused frame among its errors with that reason until a frame of the button is accepted, but while developing read the answer yourself (`render_preview`, or a one-off post) — the user should never be the one who finds it.
- **`curl -q` first, the token through `--variable`.** `-q` makes curl skip `~/.curlrc`, where another program could plant a proxy that carries the token elsewhere; `--variable '%DESMAPTIC_TOKEN='` + `--expand-header` keeps the token off the command line (see The runtime API). The answer comes back with `-w '\n%{http_code}'`: the status on the last line, the JSON before it, read by pattern (`"visible":false`, `"dropped":true`).
- **One connection for a loop that posts often.** The agent keeps a connection open between requests (closed after 30 s of silence). The template posts every few seconds, so one `curl` per post costs nothing. A script that posts **more than once a second** — a scene, a ticker, a visualizer, a loop drawing many buttons — must keep one connection open and send everything over it: in zsh `zmodload zsh/net/tcp`, `ztcp 127.0.0.1 9848` and HTTP/1.1 written by hand, reconnecting once when a request gets no answer (the spectrum example in `get_available_actions` topic `audio`); in the scene template's python the `Sender`. A new connection per post leaves a closed socket holding a port for 30 s, and at a few hundred posts a second the Mac runs out of ports and *every* script's posts start to fail. For the same reason never start `curl` per frame in such a loop.
- **On SIGTERM: remove the face and exit 0.** The button returns to its saved face (or icon and label) instead of freezing on the last value.
- **Sample cheaply.** `top -l 1` costs over a CPU-second per call; `iostat -c 2 -w 1`, `vm_stat`, `pmset -g batt`, `netstat -ib` are cheap. A widget must not be the load it measures.

## Music levels: `GET /api/audio/levels`

A widget that moves with the sound the Mac plays (spectrum, VU meter, bass glow, beat flash) does not capture audio itself: the agent does, once for every widget, and answers `GET http://127.0.0.1:9848/api/audio/levels?client={{CELL_ID}}` (the same token as the frames, the same way — never on a command line) with one line of text — `state audible bass pulse beat l0 … l19` (`state` = `ok` / `starting` / `error` / `unsupported`; numbers 0…40; `beat` 0/1; 20 log bands, 35 Hz → 14 kHz). Levels are the peak since *this* client's previous request, so pass the button's own id. Full field list and a complete spectrum script: `get_available_actions` topic `audio`.

- **At most 15 polls a second, over the one keep-alive connection** that also carries the frames (the agent analyses the sound 30 times a second, so every answer is fresh); linear easing, `duration` ≈ 1.25 × the frame interval (1.2–1.35×, the rule of continuous motion — at about 12 frames a second its extra quarter covers only ~0.02 s of Wi-Fi delay, so a burst still pauses the bars briefly; a longer glide would trail the beat). It glides continuously — one music widget per page.
- **The frame rate fits the script's own limit.** A loop that asks on every frame draws no more frames a second than it lets itself ask, and a limit counted over a window gets a margin — 16 requests a second for 15 frames. Otherwise the limit refuses one frame each second; a loop that holds that frame back leaves every glide to end early, and the picture stands still for a moment once a second. Draw such a frame from the last levels.
- **Ask only while the button is on screen — from the very start.** The script runs from the moment the phone connects, whatever page is open, so look at `GET /api/view` *before* the first levels request, and stop asking once it is hidden. A widget that sends frames only on change sends none in silence, so no `visible` comes back: look at `/api/view` when nothing went out for 2 s. The capture starts with the first request and stops 5 s after the last one, so a hidden widget costs the Mac nothing.
- **The first request makes macOS ask for permission on the Mac** — the agent never asks by itself, so your widget decides when: asking only while shown puts the prompt on the moment the user opens the widget's page (and never, for a user who does not). Tell the user. A refusal is silent: `ok`, `audible` 0, flat bars while music plays; the fix is System Settings → Privacy & Security → Screen & System Audio Recording → System Audio Recording Only → Desmaptic Agent.
- Anything but `ok`, or a 404 from an older agent → flat bars; keep the rest of the widget (title, progress) working. The track itself comes from the player via `osascript`, only if the player is already running — a bare `tell application "Music"` launches it.

## Interaction patterns

- **Toggle with live state:** tap script flips the thing and writes nothing; the loop reads the real state (`osascript`, `defaults read`, a CLI) and draws it. The source of truth is the system, not a file.
- **Timer / pomodoro:** tap writes a start timestamp to `$DESMAPTIC_STORAGE/<widget>/state`; the loop draws the remaining share as a ring and posts a notification (`/api/notify`) at zero, to the phone and the Mac (`"targets":["phone","mac"]`) — the phone shows it only while Desmaptic is open (below). Parse the state file explicitly — never `source` it.
- **Keep the Mac awake:** `POST /api/keep-awake` with `{"cellId": "{{CELL_ID}}", "minutes": N}` (or `"until"`, or `"off": true`) keeps the Mac from sleeping until then — with the same token rule, for any script. The request outlives the script and the phone and survives a restart of the agent; the display still sleeps and locks. A toggle reads `GET /api/keep-awake` first and sends `off` when its own `cellId` is among `requests`. Never `caffeinate` or `pmset` for this. Fields, answers and a complete toggle: `get_available_actions` topic `scripts` → `keepAwake`.
- **One script, many buttons:** a script may update *other* buttons by their UUIDs. A dashboard or a scene is one loop that posts to every cell (see `scenes.md`). Put it on one button of the page.
- **Notifications:** `POST /api/notify` shows a local notification on the phone and/or the Mac (title, body, up to four action buttons that run commands on the Mac). Schema: `get_available_actions` with topic `notifications`. The phone shows it while Desmaptic is open, or within about 30 s after it left the screen; after that iOS suspends the app, and the notification appears only when Desmaptic is opened, as a new one — or never, if iOS or the user closes the app first. Whenever Desmaptic is not on screen the answer says `"phone":"sent"` with `"reason":"background"`: it may not show now. Send what must not be missed (a meeting, a timer at zero, a failed build) with `"targets":["phone","mac"]`, or post it again with `["mac"]` on that reason (the phone may show it too). Actions that *run* something (a shell command, AppleScript, typed text, keys, a shortcut, a `file://` or custom-scheme URL, a system action beyond media and volume) are accepted only from a script the agent started — the button's startup, tap or long-press script, not a process that outlived it — otherwise the whole notification gets 403. The notification shows your text exactly as sent, so let each action's title say what it does. An action from the button's own script runs as soon as it is tapped, on the Mac and on the phone, like a press of that button. An action that runs something and comes from any other program on this Mac (through the agent's local socket: a hook, a terminal tool) is shown in full and runs only after the user confirms it, on the Mac and on the phone. The agent records who sent the notification itself: never put an `origin` field in the body (400). So keep each action's command a short line the user can read and recognise; for anything longer, have the script write a clearly named helper into `$DESMAPTIC_STORAGE/<widget>/` when it starts and let the action call it. Notification text shows on the lock screen and the Watch, and the system keeps it. No codes, passwords, tokens or amounts: write "New code", show the value on the button, or set `sensitive: true` (the notification then shows only the button's name and "Open Desmaptic to see it" on the phone, "Desmaptic" on the Mac, and keeps none of your text — put the value on the button; a sensitive notification may carry only dismiss actions without a command).
